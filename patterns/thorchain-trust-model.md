# THORChain trust model: bonded operator threshold custody

Lead question: who do users have to trust, and what stops the trusted parties from stealing the custodied funds?

Short answer: users trust a permissionless set of bonded node operators (roughly 100 active) to refrain from colluding above the 2/3 threshold inside the TSS vaults that custody all real (BTC, ETH, etc.) assets. The economic backstop is a 2:1 invariant where total bonded RUNE is meant to exceed twice the pooled liquidity, so a successful theft costs more than it earns (in theory). Live churn of the signer set every roughly 2.5 days plus DKG of fresh vault keys is the operational backstop. The May 2026 GG20 incident shows the cryptographic assumptions are also load-bearing, and not unconditional. See also [[projects/thorchain]] and [[patterns/signer-federation-trust]].

## Signer set composition

- THORChain validators ("THORNodes") run a full node, a Bifrost daemon (per supported chain) and a TSS daemon (https://docs.thorchain.org/thornodes/overview/node-operations, accessed 2026-05-19).
- Status pipeline: Whitelisted, Standby, Ready, Active, Disabled (https://docs.thorchain.org/thornodes/frequently-asked-questions/node-operators, accessed 2026-05-19).
- Active set size: target of around 100; the protocol defines physical vault shards as `num_physical_vaults = ceil(num_nodes / ASGARDSIZE)` with default `ASGARDSIZE = 20`, so 100 nodes implies 5 Asgard vault shards (https://dev.thorchain.org/bifrost/vault-behaviors.html, accessed 2026-05-19).
- Churn cadence: one churn event approximately every 2.5 days (43,200 blocks, `CHURNINTERVAL`); at most one new node joins per churn, selected by bond size; one or more nodes leave based on tenure, slash points, version compliance or voluntary departure (https://docs.thorchain.org/thornodes/overview/node-operations, accessed 2026-05-19).
- Minimum bond: 300,000 RUNE (`MinimumBondInRune` Mimir setting). In practice the effective threshold is the `medianActiveBond`, so onboarding is a permissionless bond auction: anyone who outbids the lowest active node displaces them at the next churn (https://docs.thorchain.org/thornodes/joining, accessed 2026-05-19).

## Threshold and signing scheme

- TSS implementation: `go-tss` wrapper around a fork of Binance's `tss-lib`, upgraded from GG18 to GG20 (Gennaro and Goldfeder 2020) ECDSA (https://dev.thorchain.org/bifrost/tss.html, accessed 2026-05-19).
- Honest threshold: signatures require at least `ceil(n * 2/3)` of the signer set in a given Asgard shard. The full private key is never reconstructed on any single host (https://dev.thorchain.org/bifrost/tss.html, accessed 2026-05-19).
- Asgard (primary) vaults hold all chain assets and are rekeyed on every churn via fresh distributed key generation (DKG). Each Asgard shard has its own TSS key and its own address per supported chain (https://thorchain-community.medium.com/under-the-hood-asgard-vaults-tss-and-node-churns-4767f3a5624b, accessed 2026-05-19).
- Yggdrasil vaults (single-node hot vaults holding up to 25% of an operator's bond) are deprecated. ADR-002 removed them and routed all outbound transactions through Asgard TSS, accepting higher compute cost in exchange for removing single-operator custody (https://gitlab.com/thorchain/thornode/-/blob/develop/docs/architecture/adr-002-removeyggvaults.md, accessed 2026-05-19; corroborated by https://docs.thorchain.org/thornodes/leaving, accessed 2026-05-19).
- DKG cadence: each churn triggers `keygen`, producing one or more vaults in `InitVault` state which then move through `Active`, `Retiring`, `Inactive` as funds migrate (https://dev.thorchain.org/bifrost/vault-behaviors.html, accessed 2026-05-19).

## Asset release flow

1. User sends a deposit transaction with a memo (e.g. `SWAP:ETH.USDC:thor1...`) to the current Asgard vault address on the source chain.
2. Each active node's Bifrost daemon observes the deposit on the external chain and posts a witness transaction to THORChain (https://dev.thorchain.org/bifrost/tss.html, accessed 2026-05-19).
3. Once 2/3 of nodes have witnessed the same event, THORChain state credits the swap, computes the output amount against the relevant CLP pools and queues an outbound transaction.
4. The outbound is batched (up to 15 messages per ceremony) and signed by the relevant Asgard shard via a TSS `keysign` ceremony requiring `ceil(n * 2/3)` participants (https://dev.thorchain.org/bifrost/tss.html, accessed 2026-05-19).
5. Each signer's Bifrost daemon broadcasts the signed transaction to the destination chain; the network monitors confirmations and migrates funds across vault generations during churn (https://dev.thorchain.org/bifrost/vault-behaviors.html, accessed 2026-05-19).

## What stops node operators from colluding to steal

- Bond:liquidity invariant. The target steady state is two-thirds of RUNE bonded versus one-third pooled (a 2:1 bond-to-liquidity ratio). The Incentive Pendulum auto-adjusts the split of swap and emission rewards between nodes and LPs to push the system back to this target (https://dev.thorchain.org/concepts/economic-model.html, accessed 2026-05-19; https://medium.com/thorchain/the-incentive-pendulum-848f3c3e4d1d, accessed 2026-05-19).
  - Note: older documentation sometimes cites "3:1" framings counting bond + LP versus LP alone. The canonical post-Yggdrasil framing is 2:1 bond:liquidity. Verified against https://dev.thorchain.org/concepts/economic-model.html, accessed 2026-05-19.
- Slashing. Bonds are slashed for `keygen` failures, missed observations, missed signing, double-signing equivalents and other operational breaches. Slashing income flows to the Reserve (https://dev.thorchain.org/concepts/economic-model.html, accessed 2026-05-19).
- Churn rotates the active set every approximately 2.5 days, generates fresh TSS keys via DKG and migrates funds to new Asgard vaults, bounding the time any specific signer subset holds the keys (https://thorchain-community.medium.com/under-the-hood-asgard-vaults-tss-and-node-churns-4767f3a5624b, accessed 2026-05-19).
- Honest threshold assumption: as long as fewer than 1/3 of nodes in a given Asgard shard collude, no outbound transaction can be signed. Combined with the 2:1 bond:liquidity invariant, a successful collusion attack at the threshold should require bonding more RUNE than the attacker can steal (theoretical EV of attack is negative). [NOT FOUND] for a current quantitative attestation of the live bond:liquidity ratio in May 2026.

## Failure modes (with real incidents)

- July 2021 ETH Router exploits (two incidents, roughly $16 million combined: roughly $7.6M and roughly $8M). Root cause was the Bifrost interface trusting smart-contract emitted events from a wrapping attacker contract, not a TSS compromise. The TSS layer functioned as designed; the bug was in how Bifrost translated on-chain events into THORChain credits (https://medium.com/thorchain/post-mortem-eth-router-exploits-1-2-and-premature-return-to-trading-incident-2908928c5fb, accessed 2026-05-19; https://www.halborn.com/blog/post/explained-the-thorchain-hack-july-2021, accessed 2026-05-19).
  - Mitigations introduced after 2021: solvency checker that auto-halts the network on observed imbalance; 25-minute node-operator timeout pause; outbound throttling; ongoing Halborn red-team retainer; Trail of Bits and Halborn audits (https://medium.com/thorchain/post-mortem-eth-router-exploits-1-2-and-premature-return-to-trading-incident-2908928c5fb, accessed 2026-05-19).
- January 2024 THORFi lending and Savers wind-down. The network paused withdrawals on BTC and ETH lending and Savers products on 23 January 2024, citing roughly $200M of net liabilities (about $97M in lending obligations, about $102M in Savers and synthetic liabilities). Root cause: the lending design implicitly took a long-RUNE position against BTC and ETH, so a drawdown in RUNE relative to those assets created uncollateralised liabilities (https://blockworks.co/news/thorchain-halts-withdrawals-insolvency, accessed 2026-05-19; https://lex.substack.com/p/analysis-thorchains-ride-from-90b, accessed 2026-05-19). A 90-day restructuring window was opened; a tokenised-liability mechanism plus a 10% protocol-fee diversion was proposed to rebuild backing (https://edge.app/blog/company-news/thorchain-savers-halts/, accessed 2026-05-19).
- May 2026 GG20 TSS exploit. A patient malicious operator (`thor16ucjv3v695mq283me7esh0wdhajjalengcn84q`) bonded RUNE, was churned into the active set within days of the attack, and exploited an implementation weakness in the GG20 ECDSA library: malformed proofs in signing rounds leaked partial key material that, accumulated over many ceremonies, reconstructed an Asgard private key. With that key the attacker signed outbound transactions unilaterally, bypassing the 2/3 threshold. About $10.8M was drained across Ethereum (3,443 ETH, about $7.77M), Bitcoin (36.85 BTC, about $2.97M), BNB Chain and Base. Network operators executed an emergency `make pause` at block 26190429 on 16 May 2026; the pause lasted roughly 13h 42m until block 26191149. The attack family matches the publicly disclosed TSSHOCK class of attacks against GG18/GG20 implementations (https://www.cryptotimes.io/2026/05/17/10-8-million-drained-inside-the-thorchain-exploit-that-froze-cross-chain-defi-for-13-hours/, accessed 2026-05-19; https://secureshift.io/blog/thorchain-exploit-analysis, accessed 2026-05-19; https://ambcrypto.com/thorchain-exploit-raises-fresh-concerns-over-mpc-wallet-security/, accessed 2026-05-19). This is the first known instance where THORChain's cryptographic, rather than peripheral, trust assumption broke.
- Earlier disclosed-but-unexploited TSS bug: a 2021 vulnerability in TSS message validation allowed two colluding nodes to publish a fake `MsgTssPool` (consensus failed to check the `.PubKeys` set against the expected ceremony set), patched in merge request 1922 and version 0.68 (https://gist.github.com/HildisviniOttar/0f931cc823837b0a239270e95e92bbca, accessed 2026-05-19).
- What happens if bond:liquidity falls below 1:1: in principle a rational majority of nodes would be incentivised to collude and drain the pools because the theft exceeds their forfeited bond. The Incentive Pendulum is designed to prevent this state from being reached by shifting rewards toward bonding before the ratio inverts, and the solvency checker halts the network on detected imbalance (https://dev.thorchain.org/concepts/economic-model.html, accessed 2026-05-19; https://medium.com/thorchain/post-mortem-eth-router-exploits-1-2-and-premature-return-to-trading-incident-2908928c5fb, accessed 2026-05-19). [NOT FOUND] for an explicit protocol clause that automatically halts deposits when bond/liquidity drops below 1:1 (as distinct from the solvency-checker behaviour).

## Comparison to [[projects/serai]] and [[projects/wormhole]] trust models

All three protocols rely on a 2/3-style honest-threshold of a signer set custodying real assets on external chains; they differ in who that signer set is and what backs their behaviour. THORChain runs a roughly 100-node, permissionless, RUNE-bonded set using GG20 ECDSA TSS across sharded Asgard vaults, rotated every approximately 2.5 days, with the 2:1 bond:liquidity invariant providing economic skin in the game (https://dev.thorchain.org/bifrost/tss.html, accessed 2026-05-19). [[projects/serai]] uses a Substrate-based proof-of-stake validator set with stake slashing, signing via FROST (Schnorr/Ed25519) and FROSTLASS (a FROST-adapted protocol for Monero CLSAG), so its threshold is also crypto-economic but uses Schnorr rather than the GG-family ECDSA implementations implicated in the THORChain incident (https://serai.exchange/2025/09/26/dkg-evrf-security-proofs.html, accessed 2026-05-19; https://github.com/serai-dex/serai, accessed 2026-05-19). [[projects/wormhole]] runs a fixed permissioned set of 19 named Guardian companies with a 13/19 supermajority and no on-chain slashing or bonded collateral; trust rests on the operators' reputational stake and Wormhole governance's ability to rotate them, not on forfeited capital (https://wormhole.com/docs/protocol/infrastructure/guardians/, accessed 2026-05-19; https://www.spark.money/tools/bridge-security-comparison, accessed 2026-05-19). In short: THORChain and Serai bond their threshold; Wormhole names theirs. All three carry the same cryptographic-implementation risk surface that the May 2026 GG20 incident materialised for THORChain.
