- [Settle a delegated batch.](https://docs.satora.io/api-reference/delegate/settle.md): The client prepares and signs delegate PSBTs (intent + forfeits), then POSTs them here. The backend reconstructs the `Delegate` struct and runs the full Ark batch ceremony on the client's behalf.

- [Create a chain-agnostic Arkade-to-EVM swap.](https://docs.satora.io/api-reference/swap/arkade/evm.md)
- [Create a new Arkade-to-Lightning swap.](https://docs.satora.io/api-reference/swap/arkade/lightning.md): Flow: 1. User provides a Lightning invoice they want paid 2. Server creates a Boltz submarine swap 3. User funds the Arkade VHTLC (returned in response) 4. Server claims the Arkade VHTLC and funds the Boltz VHTLC 5. Boltz pays the Lightning invoice

- [Create a chain-agnostic Bitcoin-to-EVM swap.](https://docs.satora.io/api-reference/swap/bitcoin/evm.md)
- [Create a chain-agnostic EVM-to-Arkade swap.](https://docs.satora.io/api-reference/swap/evm/arkade.md)
- [Create a chain-agnostic EVM-to-Bitcoin swap.](https://docs.satora.io/api-reference/swap/evm/bitcoin.md)
- [Create a chain-agnostic EVM-to-Lightning swap.](https://docs.satora.io/api-reference/swap/evm/lightning.md): Flow: 1. User provides their Lightning invoice (they want to receive BTC) 2. Server prepares Boltz submarine swap to pay the invoice 3. User funds EVM HTLCErc20 with tokens 4. Server pays Lightning invoice via Boltz (gets preimage) 5. Server claims EVM HTLCErc20 using preimage
- [Get swap status and details by ID](https://docs.satora.io/api-reference/swap/id.md)
- [Claims an EVM-targeted swap gaslessly via the HTLCCoordinator contract.](https://docs.satora.io/api-reference/swap/id/claim-gasless.md): Supports Arkade-to-EVM, Lightning and Bitcoin-to-EVM swaps. The server submits `coordinator.redeemAndExecute` on the client's behalf, using the client's EIP-712 signature and secret.
- [Collaboratively refund an EVM HTLC before timelock expiry.](https://docs.satora.io/api-reference/swap/id/collab-refund-evm.md): The client signs a coordinator-level `CollabRefund` EIP-712 message authorizing the refund parameters. The server cosigns with an HTLC-level `Refund` signature (as claimAddress, waiving the timelock) and submits the transaction on-chain.
- [Get EIP-712 parameters for collaborative EVM HTLC refund.](https://docs.satora.io/api-reference/swap/id/collab-refund-evm/params.md): Returns the addresses, amounts, and struct fields the client needs to construct and sign the `CollabRefund` EIP-712 typed data. The client signs this, then POSTs the signature to the collab-refund-evm endpoint.
- [Fund an EVM-sourced swap gaslessly via Permit2.](https://docs.satora.io/api-reference/swap/id/fund-gasless.md): The server submits the `executeAndCreateWithPermit2` transaction on the depositor's behalf, pulling tokens via the depositor's Permit2 signature. If an EIP-2612 permit is provided, the server first submits that to approve the Permit2 contract.
- [Returns the gasless claim data for an EVM-targeted swap.](https://docs.satora.io/api-reference/swap/id/redeem-and-swap-calldata.md): For non-WBTC targets: fetches fresh 1inch DEX calldata with `receiver = destination`. For WBTC-direct targets: returns only the gasless fee and calls_hash (no DEX data).
- [Returns calldata to refund an expired EVM-to-Arkade HTLC via the coordinator.](https://docs.satora.io/api-reference/swap/id/refund-and-swap-calldata.md): Two modes: - `mode=swap-back` (default): calls `refundAndExecute` — refund WBTC from expired HTLC, swap   WBTC → source token via 1inch, sweep to caller. - `mode=direct`: calls `refundTo` — refund WBTC directly to caller (no DEX).
- [Returns structured data for funding an EVM-to-BTC swap via Permit2.](https://docs.satora.io/api-reference/swap/id/swap-and-lock-calldata-permit2.md): Instead of pre-encoded calldata, this returns the individual components so the SDK can construct the Permit2 EIP-712 signature and `executeAndCreateWithPermit2` calldata client-side.
- [Create a new Lightning-to-Arkade swap.](https://docs.satora.io/api-reference/swap/lightning/arkade.md): Flow: 1. User pays the Lightning invoice returned 2. Server receives BTC via Boltz and creates Arkade VHTLC for user 3. User claims Arkade VHTLC with secret, revealing it 4. Server claims Boltz VHTLC with the revealed secret
- [Create a chain-agnostic Lightning-to-EVM swap.](https://docs.satora.io/api-reference/swap/lightning/evm.md)
- [Recover swaps by deriving user_id keys from an Xpub](https://docs.satora.io/api-reference/swap/recover.md): This endpoint allows clients to recover their swap history after importing a mnemonic. The client provides an Xpub they used to derive `user_id`s, and the server derives `user_id` keys at m/9419/121923/<index> from the requested start index until the server-owned gap limit or scan cap is reached.
- [Get list of available tokens for swaps.](https://docs.satora.io/api-reference/tokens.md): Optionally pass `source_chain` + `source_token` **or** `target_chain` + `target_token` to filter the response to valid counterparty tokens.
